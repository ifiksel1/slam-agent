BIEVR-LIO = ethz-asl "Bump-Image-Enhanced Voxel maps" LIO (RSS 2026, arXiv 2604.14421), same lab as COIN-LIO. Targets degenerate/feature-sparse geometry — directly relevant to [[hangar_737_inspection]]. Pure LIO, **no explicit loop closure**; keeps a persistent voxel-image map (implicit closure on revisit).

**⭐ MECHANISM — ground-truth from source read 2026-07-12 (corrects an earlier verbal mischaracterization that called it an ESKF with Zhang-style degeneracy detection — BOTH WRONG):**
- **NOT a Kalman filter.** Estimator = hand-rolled **Levenberg-Marquardt** SE(3) scan-to-map registration (`src/ls_optimizer.cpp:163` `stepLm`, built on DLIO's nanoGICP) + a **separate Ceres sliding-window** graph for velocity/bias/gravity with **poses held constant** (`src/pipeline.cpp:285` `optimizeInertialWindow`, `SetParameterBlockConstant`). Loosely coupled: LM solves pose, Ceres window refines inertial state. NO IKFoM/esekfom anywhere (unlike COIN-LIO & EllipseLIO which are FAST-LIO2 IKFoM).
- **Map** = hash voxel map (`ankerl::unordered_dense`), each `Voxel` stores a plane-aligned **height ("bump") image** `bump_img_/bump_smoothed_` + plane frame (`include/bievr_map.h`, `src/bievr_map.cpp`), LRU eviction. NOT an ikd-tree, NOT raw points.
- **Residual** = purely geometric+inertial, NO intensity/photometric channel. Point transformed into voxel plane frame → in-plane `(x,y)`, height `z`; residual `r = z − I(x,y)` where `I` is the bilinearly-sampled bump image (`src/ls_optimizer.cpp:114`). Jacobian **subtracts the height-image gradient chained through in-plane rows** (`ls_optimizer.cpp:112`) — THIS is what constrains the tangential/sliding DOFs a flat plane leaves free. Mechanistically the SAME trick as COIN-LIO (image-gradient term in the Jacobian) except the "image" is a GEOMETRIC height map in map-frame, not photometric intensity in sensor-frame → they are cousins, not opposites.
- **Degeneracy handling = BY CONSTRUCTION, not detection.** Grep confirms ZERO eigenvalue/Hessian degeneracy detection, NO solution remapping/gating/clamping (the only eigensolver is per-voxel normal estimation). Robustness comes from (1) the bump-gradient residual enriching weak directions, (2) map-informed point sampling (`sampleInformed`, keeps ALL points from high-"bump-texture" voxels, one from flat ones — `src/preprocess.cpp:68`), (3) passive LM damping + gravity prior.
- **Determinism is DELIBERATELY ENGINEERED (explains the byte-identical result):** uses **TBB `parallel_deterministic_reduce`** (`ls_optimizer.cpp:61`, fixed reduction tree) + explicit tie-break sorts ("deterministic order"), NO OpenMP. This is the architectural OPPOSITE of EllipseLIO's OpenMP+atomic-row-order nondeterminism ([[coinlio-ellipselio-photometric-fusion]]).

**⭐ SENSOR-AGNOSTIC / Hesai JT-128 compatibility (source read 2026-07-12): YES, config-only, no code changes.** BIEVR's core point type is `StampedIntensityPoint` = xyz + per-point time + intensity ONLY (`include/bievr_lio/common.h:24-28`) — NO ring/ambient/reflectivity/range fields, no spherical-projection LUT, no `lidar_type` switch (the bump-image voxel map is built in MAP frame → sensor-model agnostic). The ROS converter (`interfaces/ros_common/include/bievr_ros_common/conversions.h:129-134,266-279`) AUTO-DETECTS the per-point time field: `t`(uint32 ns rel, Ouster) / `time`(f32 s, Velodyne) / `timestamp`(f64 abs, **Hesai — explicitly labeled**). A Hesai config already ships (`config/sensor_configs/grandtour.yaml`, Hesai XT32). So JT-128 works with: (1) new sensor-config YAML (pointcloud/imu topics, extrinsics, `max_range_m`~40-60 not 100); (2) **IMU: the JT-128 HAS a built-in, hardware-synced 6-axis IMU (user-corrected 2026-07-12)** — the Hesai driver publishes it on its own IMU topic, so this is drop-in like the OS1's `/ouster/imu`, NOT an external-IMU integration task. Just wire the IMU topic in the YAML, set `T_IMU_LIDAR` from Hesai's mechanical drawing (integrated IMU → fixed known extrinsic, not a field-calibration), and set IMU noise params. Verify the driver's IMU axis/orientation convention. (3) time-base sanity: JT-128 `timestamp` is f64 absolute (PTP/GPS) — ensure driver header stamp shares that base or the ">0.5s span" warning (`conversions.h:344`) fires (hardware-synced IMU makes this largely moot since lidar+IMU share the sensor clock). Per-point timestamps are REQUIRED (converter hard-fails without t/time/timestamp; used for IMU-predicted undistortion `src/undistort.cpp`). Intensity is optional (zero-filled if absent; estimator doesn't use it). **Verdict: genuinely config-only / near drop-in — no code changes, no external IMU. Remaining work = sensor-config YAML + T_IMU_LIDAR extrinsic + IMU noise params + a live time-base/orientation sanity check.**

**⭐⭐ 12 REAL 737-HANGAR BAGS (2026-07-13, `~/all_bag_files/`, the ACTUAL [[hangar_737_inspection]] target data — Ouster OS1-64, same auto-orientation config as 3rd_floor). ANSWER TO "does 1.35cm hold or is 3rd_floor easy?": 3rd_floor was EASY. BIEVR FAILS on the 737 geometry.**
- Ran BIEVR once/bag (determinism already settled, 27 prior runs). Results in `/home/dev/bievr_ws/results/all_bags/` + merged table `results/rto_report.json`.
- **On the 5 bags where the drone provably returned to ~0.1-0.3m (ICP + onboard-EKF cross-confirmed), BIEVR's true drift was: 0.44m (short 15m flight), 5.9m, 10.6m, 11.1m, and 298m (runaway).** Even the best (0.44m) hit a 4.84m mid-flight peak — its tight endpoint was partly luck.
- **⭐ THE ONE "SUCCESS" IS TRIVIAL (user caught 2026-07-13):** cmem3_02-03-32 (the 0.44m bag) is a NEAR-STATIONARY HOVER, not a flight: 72% of the time within 0.3m of start, 95% within 0.52m, only 15.6m total path over 9min, one brief 4.84m excursion. Returning to origin is trivial when you barely leave it. So BIEVR does NOT have "1 success + 11 fails" — it has **ZERO successes on any real-motion 737 bag**, plus one hover that doesn't count. Cleaner conclusion: pure LIO is not viable on the 737 geometry, full stop. (Detection: `scripts/trim_bag.py --dry-run` reports per-bag motion window; direct motion stats via /mavros/local_position/pose.)
- **2 outright NUMERICAL DIVERGENCES**: 737_700_TAIL → 863,700m, cmem3_00-38 → 362,934m. Silent (no NaN/warning in log). The rest: 18-649m unbounded monotonic drift.
- **Ruled out data dropout** (the [[lidar_field_recording_dropout]] confound): gap-checked the 2 runaways + FRONT — LiDAR clean 20Hz (max gap 0.065s), IMU 100Hz (max 0.022s), ZERO gaps>0.3s. **Data is pristine → the divergence is the ESTIMATOR, not the bags.**
- **Root cause = consistent with BIEVR's design**: it has NO degeneracy detection/gating "by construction" (grep-confirmed above). The 737 hangar = large smooth surfaces (fuselage skin, floor, walls) = geometric degeneracy → the bump-image-gradient robustness is INSUFFICIENT, and with no gating the LM slides/diverges unbounded. This is the failure mode the design bets against, and the bet loses on real hangar geometry.
- **CONSEQUENCE**: hard evidence that pure LIO — even the best-behaved deterministic one — is NOT viable standalone in the 737 hangar. Directly validates the [[hangar_737_inspection]] architecture decision (LIO + absolute anchor + degeneracy gating, NOT pure LIO). Do NOT stake the hangar mission on BIEVR alone.

**⭐ PHASE-7 TUNING DONE (2026-08-31) — BIEVR WAS NEVER TUNED, AND STOCK WAS COSTING UP TO 32x.** The July "next probe" (tune max_range/voxel -- is the divergence fundamental?) was never run; every hangar number was stock, in a sensor config whose own comment reads "Indoor 3rd_floor / apartment". **The lever is `map/pixel_size_m`: 0.05 (stock) -> 0.40 gives 10.639 -> 0.334 m** on 737_MAX_8_LIO_SAM_3. Full deterministic response curve (repeat at 0.20 was bit-identical): 0.05->10.639, 0.10->4.517, 0.15->4.645, 0.20->0.369, 0.25->1.158, 0.30->0.361, 0.40->0.334. Erratic in the middle (the 0.25 bounce is REPRODUCIBLE, not noise) but a plateau above 0.20. **Tuning also made it REAL-TIME: 1.2-2.5x faster than realtime at pixel 0.40, vs ~0.67x at stock** -- one parameter fixed accuracy AND speed. Two arms are unusable: `pixel_size 0.025` **OOM-kills** the 8GB Orin (1.5M-voxel budget), and `downsample_resolution_m 0.05` **DIVERGES to 4407 m** -- more points made it 400x worse. The July hypothesis ("finer voxel for more bump-texture") was BACKWARDS in both dimensions; COARSER wins, as it did for GenZ-ICP.
Validation of pixel 0.40 across the 4 GT bags: **0.334 / 0.434 / 4.018 / 0.452 -- 3/4 sub-metre, median 0.443.** Note it does NOT transfer perfectly (cmem9gs5j wants its own optimum), so a per-bag sweep would likely do better still. **⚠️ SUPERSEDED IN PART (2026-08-31).** The conclusion "pure LIO is not viable standalone in the hangar" was drawn from BIEVR's behaviour alone and does NOT generalize. LiDAR-ONLY **GenZ-ICP**, after fixing broken upstream solver defaults, achieves 20 Hz with 100% scan capture and **sub-metre true drift on all 6 scorable bags (median 0.35 m)** on this exact dataset — including **0.096 m where BIEVR scored 298 m** (that 298 m is a STOCK number -- see Phase-7 above; tuned BIEVR was not re-run on that bag). BIEVR's km-scale divergences were near-singular solves that GenZ's point-to-point identity-Hessian term structurally prevents. What still stands: BIEVR's own numbers, the tiering, and `icp_return_gt.py`/`rto_report.py` as the scoring tools. See [[genz-icp-evaluation]].
