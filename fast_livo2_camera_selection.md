Building **FAST-LIVO2** (LiDAR-inertial-visual odometry) on: Jetson Orin NX 16GB on a **Connect Tech Hadron-DM (NGX024)** carrier (TNSPEC `cti-orin-nx-ngx024`), **L4T 35.4.1 / JetPack 5.1.2 / Ubuntu 20.04**, with **Ouster OS1-64** LiDAR and **CubeOrange** (ArduPilot). Existing validated profiles on this platform are FAST-LIO2 (LiDAR-only) — the visual leg is new.

FAST-LIVO2 hard requirements that drive camera choice: **global-shutter** sensor + **hardware external trigger** (camera exposure slaved to LiDAR). Plan: drive camera trigger from Ouster `SYNC_PULSE_OUT` (multipurpose-IO, `OUTPUT_FROM_INTERNAL_OSC` @ 10 Hz; opto-isolated open-collector, needs external pull-up) — no STM32 sync board needed. Run camera fixed-exposure + auto-gain. Prefer **mono IMX296** (direct/photometric method uses grayscale).

Three candidate camera paths:
- **CTI IMX296 driver** — sensor+carrier known-good (CTI BSP added IMX296 at r35.3.1); trigger capability = the open question.
- **VC MIPI IMX296** (Vision Components hardware+driver) — external trigger is first-class (`trigger_mode=1` V4L2 + DT param), IMX296+OrinNX+L4T35.4.1 all supported, BUT Hadron NOT a listed carrier (only NVIDIA devkits + Auvidea) → needs custom device-tree port using CTI's lane mapping.
- **USB3 industrial** (Hikrobot/Blackfly global shutter) — carrier-agnostic, trigger guaranteed, heaviest; the zero-risk fallback if both CSI paths stall.

**Why:** the CTI carrier (not an NVIDIA devkit) makes CSI a BSP+device-tree task, not plug-and-play; the trigger answer decides CSI-vs-USB3.
**How to apply:** when the user returns with CTI's reply — trigger-supported → CTI IMX296 mono; free-running only → VC MIPI (port DT) or USB3. Then proceed into Phase 1 assessment. Related: [[coinlio_workspace]] (prior LiDAR-visual work), [[slam_comparison]].
